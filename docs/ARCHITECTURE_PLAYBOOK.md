# Architecture & Onboarding Playbook — WB FBS Manager Multi-Agent System

> **Версия**: 1.2.0  
> **Статус**: Production Standard  
> **Назначение**: Руководство по архитектуре мультиагентной системы, фреймворку безопасности (PoLP), регламенту управления агентами, устойчивости развертывания и защите ресурсов.

---

## 1. Введение и Обзор Архитектуры

Сервис **WB FBS Manager** представляет собой мультитенантную платформу для автоматизации торговли на Wildberries по схеме FBS с обязательной маркировкой «Честный Знак» (ГИС МТ).

Мультиагентный слой построен на базе асинхронного брокера задач **Celery + Redis** и предназначен для изолированного, параллельного и отказоустойчивого выполнения специализированных бизнес-процессов.

### 1.1 Топология и Матрица Агентов

Система включает 11 специализированных агентов:

| Идентификатор | Имя Агента | Очередь Celery | Триггер / Расписание | Назначение |
|---|---|---|---|---|
| `order_poller` | Order Poller Agent | `orders` | Каждые 60 сек | Опрос новых сборочных заданий WB API, проверка КИЗ, скачивание стикеров |
| `supply_agent` | Supply & Shipment Agent | `supplies` | Событийный / Manual | Формирование поставок, добавление заказов, привязка ШК, закрытие поставок |
| `cz_withdrawal` | CZ KIZ Withdrawal Agent | `cz_operations` | Ежедневно в 03:00 / Событийный | Вывод КИЗ (SGTIN) из оборота в ГИС МТ (True API) с подписью КриптоПро УКЭП |

## 2. Фреймворк Принципа Минимальных Привилегий (PoLP)

Все агенты функционируют в рамках строгого принципа наименьших привилегий (Principle of Least Privilege — PoLP). Настройки и матрицы прав консолидированы в едином манифесте [`agents_config.json`](file:///d:/PyCharm_Projects/WB%20FBS/agents_config.json).

### 2.1 Конструкция Манифеста `agents_config.json`

Манифест содержит 3 ключевых слоя безопасности:
1. **Global PoLP Policy**: Запрет чтения/записи к `.env`, сертификатам `*.pem`, `*.key` и системным директориям OS.
2. **Per-Agent PoLP Matrix**:
   - `allowed_read_paths`: Разрешенные пути/шаблоны файлов для чтения.
   - `allowed_write_paths`: Разрешенные пути/шаблоны файлов для записи.
   - `allowed_delete_paths`: Явно разрешенные пути для удаления (доступно только агенту `cleanup`).
   - `forbidden_paths`: Пути, строго запрещенные для данного агента.
   - `database_table_permissions`: Разрешенные SQL-операции над таблицами (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
   - `external_api_access`: Разрешенные внешние точки интеграции (`WB_MARKETPLACE_API`, `GIS_MT_TRUE_API`, `TELEGRAM_BOT_API`).
   - `crypto_key_access`: Доступ к ключам подписи (`NONE`, `READ_DECRYPT_TOKENS`, `USE_UKEP_SIGNATURE`).
3. **Arbitration Rules**: Веса приоритетов очередей, лимиты параллелизма и параметры распределенных блокировок Redis.

## 3. Регламент Защиты Ресурсов и Памяти (OOM Defense)

Для стабильной работы на серверах со скромными характеристиками (1 CPU / 1 GB RAM) действуют обязательные системные правила:

1. **Обязательный Swap (2 ГБ)**: Файл `/swapfile` активируется автоматически в `setup_vps.sh` и `deploy.sh`. Это исключает OOM-сбои при пиках сборки Docker или запуска воркеров.
2. **Автоматический рециклинг воркеров Celery**:
   - `--max-memory-per-child=120000` (120 МБ) — дочерний процесс автоматически перезапускается при превышении лимита памяти.
   - `--max-tasks-per-child=50` — регулярное освобождение памяти от накопленных структур Python.
   - `--concurrency=1` — строгий лимит параллелизма на 1-ядерных серверах.
3. **Cgroup лимиты памяти в Docker Compose**:
   - `worker`: 300M
   - `api`: 280M
   - `postgres`: 180M
   - `bot`: 100M
   - `scheduler`: 80M
   - `redis`: 64M
   - `nginx`: 48M

## 4. Регламент Развертывания и Nginx DNS Resolution (Zero-Downtime Deploy)

Для предотвращения ошибок 502 Bad Gateway и рассинхронизации маршрутов:

1. **Динамический DNS Nginx**:
   - В `nginx/conf.d/app.conf` настроен `resolver 127.0.0.11 valid=10s ipv6=off;` с переменной `$upstream_api http://api:8000;`.
   - Nginx переопределяет IP-адрес API-контейнера каждые 10 секунд и никогда не проксирует на устаревший IP.
2. **Монтирование конфигураций Nginx**:
   - В `docker-compose.prod.yml` монтируются оба файла: `./nginx/nginx.conf` (зоны rate-limiting) и `./nginx/conf.d/app.conf`.
3. **Атомарный скрипт обновления (`scripts/deploy.sh`)**:
   - Использует `docker compose up -d --force-recreate` для гарантированного обновления всех контейнеров и сетей.
   - Выполняет опрос эндпоинта `/health` до 60 секунд.
   - Проверяет доступность порта 80 и работу входа администратора.

## 5. Самовосстанавливающаяся Аутентификация (Unbreakable Auth)

1. **Master .env Fallback (Strategy B)**: Если хэш в базе данных рассинхронизирован, пароль из `.env` (`ADMIN_PASSWORD`) действует как мастер-ключ и автоматически обновляет хэш в PostgreSQL.
2. **Автоматическое восстановление**: Если учетная запись `admin` отсутствует или была отключена (`is_active=False`), система автоматически восстанавливает и активирует её при попытке входа.
3. **Гигиена ввода**: Фронтенд автоматически применяет `.trim()` к логину и паролю.
4. **Точная обработка HTTP-статусов**: Фронтенд явно разделяет HTTP 401 (неверный пароль) и HTTP 502/503 (сервер недоступен).

## 6. Изоляция CLI-Скриптов

Все скрипты обслуживания, запускаемые на хосте (`scripts/set_admin_password.py`, `scripts/backup_db.sh`, `scripts/deploy.sh`):
- Имеют **нулевые внешние зависимости** Python на уровне хоста (используют только `sys`, `os`, `re`, `subprocess`, `shutil`, `pathlib`).
- Автоматически пробрасывают выполнение внутрь работающего Docker-контейнера через `try_docker_forward()`.

## 7. Регламент Уведомлений об Обновлении на VPS (VPS Update Policy)

При внесении любых изменений в проект (код бэкенда, фронтенд, Celery-агенты, миграции базы данных, Nginx или переменные окружения) агент **в обязательном порядке** прикрепляет в итоговом сообщении пользователю пошаговую инструкцию по накатыванию обновления на боевой сервер (VPS):

1. **Команды загрузки изменений**:
   ```bash
   cd /opt/wb_fbs
   git pull origin main
   ```
2. **Применение обновлений и миграций**:
   ```bash
   bash scripts/deploy.sh
   ```
   *(Скрипт `deploy.sh` автоматически применит миграции `alembic upgrade head`, пересоберет нужные контейнеры без простоя, проверит `/health` и статус сервисов).*
3. **Проверка работы**:
   ```bash
   docker compose -f docker-compose.prod.yml ps
   docker compose -f docker-compose.prod.yml logs --tail=50 -f api worker
   ```
